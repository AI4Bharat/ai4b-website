    Inside Indic-Speak

    A 3.36B language model where punctuation shapes timing, pauses, and emphasis.

    Most text-to-speech systems move through a long pipeline: letters to phonemes, phonemes to durations, durations to acoustic features, features to sound. Indic-Speak takes a shorter route. Give a language model audio codes in its vocabulary, and speaking becomes something it already knows how to do: continue the sequence.

    On this page

      At AI4Bharat we have worked on Indian language AI for years, and have open-sourced translation, speech recognition and speech generation across all 22 languages. Speech itself was never the missing piece. Reading that sentence was — the one that changes script mid-clause, the way people actually write. That is the gap we set out to close.

      Today, as a joint effort between Bodhan AI and AI4Bharat, we are introducing Indic-Speak: a text-to-speech model built to read text exactly as it is written, across 22 Indian languages and 12 scripts.

      The idea

      One decision explains the system: make audio part of the vocabulary, and speech becomes a next-token problem.

      01 Put speech inside the vocabulary

      Start with a Llama-3.2-3B decoder that already models Hindi and English in one token stream. Add 28,672 codes from a neural audio codec. Train the model to continue a written sentence with those codes instead of more words. Text goes in; the next token begins a voice. The rest of the system follows from that choice.

      The consequence worth sitting with is what the model does not need. No phoneme dictionary per language, so a new script costs no frontend work. No aligner, so training needs no phoneme-level timing. No duration predictor, because length is simply how much the model generates before it stops. And no language decision anywhere in the request path: text arrives as written, code-mixed or not, and the tokeniser that already handled both halves of a Hindi-English sentence handles it unchanged.

      What it keeps is everything a text decoder already had. Attention reaches across the whole utterance, which is the mechanism behind punctuation acting as prosody: a clause can be shaped by a comma thirty words earlier. The 131,072-position context makes a long passage a budget question rather than an architectural one. And sampling behaves as it does for text, so the settings that make prose livelier make speech livelier and less reliable in the same proportion.

      The 28,672 codes occupy one contiguous run in the middle of the vocabulary, ids 128,266 through 156,937. That contiguity does real work: telling speech from text at decode time is a range check on the token id, not a second output head and not a structure signal. Control tokens were placed below the run and conditioning tokens above it, so the added entries are deliberately not contiguous with each other. Code that assumes everything added sits above the base vocabulary is wrong here.

      A request is a chat-template prompt carrying the speaker name, an optional style tag and the normalised text. The model answers by opening a speech span and then emitting audio codes until it stops. Everything after that point is deterministic: the flat stream de-interleaves into codebooks, the codebooks become latents, the latents become sound.

      The machine

      What actually runs at inference, counted rather than quoted, and where each of the three pieces starts and stops.

      02 Three pieces. One speaking model.

      Three components execute when you make a request, and the language model is 98% of the parameters. The other two are small by design: one is a lookup table, and one is a vocoder that was fine-tuned rather than trained from scratch.

      model

      Llama-3.2-3B backbone

      Parameters — 3.301 B in the backbone; 3.359 B across everything that runs at inference, counted per component below
      Vocabulary — 156,960 tokens: 128,256 text plus 28,672 audio codes and a small set of speaker, style and non-verbal tokens, with input and output embeddings tied
      Audio frame — 7 codec tokens per 85.33 ms frame, 82.03 tokens per second of speech
      Context — 131,072 positions, so length is a budget rather than a limit

      audio

      SNAC codebooks, Vocos decoder

      Codebooks — SNAC's quantizer at 24 kHz, three codebooks at a 1:2:4 time ratio flattened into one token stream. Only the codebooks are used, to turn generated codes back into latents: 0.14 M parameters
      Decoder — those latents go straight to a fine-tuned Vocos decoder, 58.4 M parameters. SNAC's own encoder and decoder are never in the path
      Output — 16-bit PCM at 24 kHz, streamed as it is generated

      serving

      One request, streamed

      Request — text, voice, optional style, optional sampling settings; the language is inferred from the text
      Length — about 30 s of speech per request, a 2,520-token ceiling; a request takes the text you give it, and splitting longer passages is the caller's job
      Defaults — temperature 0.6, top-p 0.9, top-k 50, repetition penalty 1.2. The conservative end of the sweep, chosen for the lowest defect rate; the livelier settings carry several times the failure rate and vary more between seeds

      03 Why an LLM—and what it costs

      A purpose-built acoustic model with a phoneme frontend was the alternative, and for one language it would have been the safer engineering. Three things made the language-model route the better bet for twenty-two of them.

      • 01Code-mixing costs nothing. A phoneme frontend has to know which language a span is in before it can look anything up, and Indian text mixes scripts inside a clause. A backbone that already tokenises both halves needs no such decision, so the hardest case for a pipeline is the default case here.
      • 02Punctuation is already prosody. The model treats a comma as a boundary and a question mark as a contour because it learned that from text. A pipeline has to be told, usually through a hand-built feature.
      • 03Length is a budget, not a redesign. A multi-minute utterance becomes a sequence-length question with a known answer: 82.03 tokens per second of speech against 131,072 positions.

      The cost lands on measurement. Generation is sampled, so output varies between runs, and a rare bad sample still sounds like fluent speech: clean audio, wrong words. A signal-quality metric cannot see that failure at all. So the evaluation reads transcripts and scores content rather than measuring the waveform, and reports the shape of the distribution rather than only its mean.

      04 From one POST to a speaking voice

      One POST, one stream, no state. The shapes below are settled. The endpoint path and the auth header are placeholders until the public URL is announced.

      Send one clean request

      POST /v1/audio/speech
Content-Type: application/json

{
  "prompt": "भारत एक हज़ार नौ सौ सैंतालीस में स्वतंत्र हुआ।",
  "model": "bodhan-tts",
  "voice_clone_id": "Amit",
  "style": "news"
}

      Only the text is required. The voice defaults to Amit, and omitting the style gives the conversational register, which is the right choice for plain reading. Sampling fields are optional and forwarded as given; the defaults are temperature 0.6, top-p 0.9, top-k 50 and a repetition penalty of 1.2, with a token ceiling matching the 30-second window. A voice or style outside the accepted lists is rejected rather than approximated, so validate against those lists client-side.

      Caveats

      Behaviours that will surprise a caller, each against the parameter it applies to. These are properties of the interface, not of the audio.

      Stream the voice back

      Audio arrives as server-sent events while it is being generated, each carrying base64 of raw PCM16, signed little-endian, mono, 24 kHz. No WAV header and no length prefix, so a client concatenates windows in order. Four details decide whether that client is correct.

      • 01Concatenate, do not overlap-add. Consecutive windows do not overlap, so crossfading them smears the output.
      • 02Payload sizes vary. The first event carries two frames and later ones carry one, so a fixed-size read breaks on the second event.
      • 03Some payloads are empty. Skip them rather than reading an empty window as end-of-stream.
      • 04Require the terminator. A stream that ends without the done sentinel failed mid-generation, and the status line already said 200. Its absence is the only signal you get.

      Splitting long text is the caller's job. A request synthesises what it is given, and more than about 30 seconds of speech will truncate rather than continue.

      Write for a listener, not a parser

      A model that reads text as written has to be handed text a person would actually say out loud. Nobody says "one two three comma four five six point seven eight rupees", and nobody says "backslash int". The normaliser in front of the model turns written notation into spoken words first, and it is the part of the stack that does the least glamorous and most necessary work.

      05 Know the edges before you ship

      The first seven describe the model and the evidence behind it; the last three are practical integration details. All are measured on the deployed endpoint, and each points to either a clear operating choice or an area still in progress.

      • 01Voice quality varies. Across the library the judge mean runs from 4.53 to 4.96. The weakest voice earns the top band on 68% of its readings against 97% for the strongest, and needs a second take on 2.7% of them against 0.3% — about nine times as often. The recommended voice for each language stays out of the thin end of that range, so start there rather than picking at random.
      • 02Native casting remains the most accurate choice. A voice reading its own language scores 4.94, with 95.7% of readings in the top band and 0.4% needing a retake. The same voices reading other languages score 4.90, 92.9% and 0.7%. Cross-lingual casting still works well; this is the small tradeoff behind the accent you hear.
      • 03Benchmark coverage currently spans ten languages. The other twelve have voices and playable audio, but not yet the same scored evidence. Treat them as supported and still being measured, rather than assuming they match the benchmarked set.
      • 04The headline measures content fidelity. Automatic transcription struggles with this code-mixed text: character error rate lands within two points of itself for the voice that scores 4.96 and the voice that scores 4.53, which means it is measuring the recogniser rather than the model. We therefore publish an LLM judge's fidelity score; its top band means “no meaningful content error”, not “word-perfect”.
      • 05Naturalness testing is still in progress. Every figure here measures whether the text was read correctly. We are not yet making a comparative claim about listening preference or voice quality; those tests are running and will be published separately.
      • 06Most readings work first time; 0.7% need a retry. That is 211 of 30,000: a repeated phrase, a dropped clause or a number that drifts. The API exposes no seed parameter, so a retry draws a fresh sample rather than reproducing the first one.
      • 07Long passages currently need splitting. One request covers about thirty seconds of audio. The five-and-a-half-minute chapter above is seven requests, split at punctuation and joined by the caller; single-pass multi-minute generation is on the roadmap.
      • 08Style tags are exact API values. children’s stories works; Children’s Stories returns a 422. Emotion tags are lowercase and the customer-care tag is title case, so validate against the published list rather than deriving a tag from display text.
      • 09Choose the language for spoken numbers. Latin digits inside an Indic sentence default to English words unless the sentence language is passed to the normaliser or the digits are written in native script. number_lang is a constructor argument, not a per-call one.
      • 10Use retry-and-backoff under sustained load. At a 1,200-per-minute ceiling, 1.7% of 70,931 request starts were rate-limited and all succeeded on retry. Accuracy did not move with load; a client should simply treat backoff as part of the normal request path.

      06 The next token is only the beginning

      The current design is deliberately simple, but it is not finished. These are the gaps we are working on next. We are not attaching dates; each improvement lands here when it holds up to the same evidence as this release.

      Teach the model to think before it speaks

      thinking TTSToday the prosody of a reading comes from what you send: the punctuation carries the breaths and a style tag sets the register. Next the model reasons about the context before it speaks and decides those for itself — where the emphasis belongs, which clause to slow down, what register the passage is actually in — so one sentence reads differently as a news bulletin, as a bedtime story, and as an answer to someone who sounds worried.
      preference studyPreference ranking against other Indian-language speech systems, on the code-mixed text these voices are built for. This is the naturalness evidence the limitations above say we do not yet have; it is running now and will be published here whichever way it comes out.

      Make the voice easier to ship

      smaller modelA smaller, cheaper Indic-Speak: the same voices and the same languages at a fraction of the cost per second of audio, so speech can sit inside an interactive product or a modest deployment budget rather than only inside a batch job.
      expressive voicesVoices built for range rather than neutrality — laughter, hesitation, warmth, urgency, and the shifts inside a single passage that separate a person talking from a narrator reading. More voices in each language arrive with them.
      long formSingle-pass generation of multi-minute passages, so a chapter is one request instead of a split-and-join by the caller.
      timestampsWord-level timestamps in the response, for subtitling, read-along and anything that has to line text up against audio.
      The architecture is compact; the ambition is not. If one model can read the scripts and language mixtures people already use, the interface to speech becomes radically simple: send the words, choose a voice, and let the next token speak.
